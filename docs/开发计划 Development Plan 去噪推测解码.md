# 三、下一轮优先级与验收
本轮只执行上述有具体证据的工程债务修复。Tracker曲线读取与新鲜度两条ponytail注释记录的是不同合同的已知成本边界，并非过期TODO，不因诊断日志分段删除它们。泛型Registry/Config抽象、稳定CLI薄入口和不同生产入口的相似测试不列为冗余。未找到现成Python3.10环境，实机验证仍缺；不扩扫描或安装。诊断分段不授权删除旧Run或自动清理，全部保留的总量、保留期及日志故障隔离仍须独立处理。下列研究结案与来源边界保持冻结，不据此重启或扩搜。
1. **受测合同结案**：已有独立CUDA参考、真实提交时序、EMA实际末状态和Kalman observation-only按研究计划声明范围完成。当前无阻断结论的具体合同缺口，不将这些已通过项重复排为待跑；未测模式、精度或理论假设保留边界，不因实现名称宣称最优性。
2. **高价值Run与方案收束**：对齐原件、配置、模型/输入、实际设备、完整/partial终态和质量/收益/时长；新收束摘要只引用旧身份。来源缺失严格拒绝，不用当前helper或相近字节补签。成功项不重跑；负研究结果和执行失败分开。
3. **仅修直接阻塞研究结案的工程缺口**：报告/计数/来源、配置与启动、CUDA设备传播和状态恢复按具体消费者处理。需要真实模型诊断先按研究计划最小预算；未定效益比较的单位/预算先在唯一计划明确，不派发旧72、范数/配对长矩阵。
4. **低价值Study与冗余清理**：队列和归档职责已整理，本回合不做物理裁剪。后续确需删除/归并时先核消费者、固定source lock与取证依赖，保第三方字节与原始数据，不以清理名义删除未知来源。
5. 测试level/target/cost按实际消费者继续细化；Python3.10待现成环境，日志总量/期限/失败隔离待明确保全与业务失败合同后推进。已完成的逐条读取/分段与11项日志元数据不重复排为待办，也不将其推广成全部日志规范落地。测试通过只证明对应合同，不等于算法有效或远端CI通过。
