# 一、问题与检索边界
要比较的问题是：不训练额外起草器时，同一目标模型怎样提出多个 token，以及什么证据能把接受效率、正确性和速度分开。

已读材料限于 ESP v2 的指定章节，以及 Leviathan、Chen、Medusa 的摘要级阅读，EAGLE、PLD、Spec-Bench 的公开 README。没有做新的引文追踪，也没有把“未核验到作者代码”写成“作者从未开源”。

# 三、ESP 的主张和本仓能核对的部分
论文主张用 prompt embedding 均值初始化 mask，并以新 token 更新；候选按累计概率成树，剪枝连续重复 token。Table 1 给出特定设置下的 τ。正文、表和附录里的输出长度与硬件需要按实验分别对齐，不能拼成一个合同。

本仓能核对的是自己的非官方实现和已归档运行，不是作者当时的输入模板、权重和聚合权重。8B 独立复验的数字在运行记录，论文目标没有达到。第三方 HF 树 `ad76f8da29f3bfc7faa20488193c6aa83a9f708c` 保留在源码中的 upstream 目录，许可状态未确认，不能称为作者官方实现。

# 四、和 10 月 31 日问题的缺口
会议背景把下一步放在 trajectory 预测与 verify observation 的联合。已读文献没有给这个联合更新提供可直接照搬的状态方程。EAGLE 的特征外推需要专门模型，ESP 的均值更新只使用已提交 embedding，Leviathan/Chen 的论证针对辅助模型或拒绝采样。

因此，联合更新的公式不能从这些论文的名称推出来。长距离外推、中间层校正、diffusion 或 flow matching 也没有在本次阅读中成为已验证路线。它们留在研究计划的后续探索，不进入当前文献结论。
